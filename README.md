# Agent Readable System (ARS)

### A Shared Language for Agents, Applications, and Operating Systems

**让 AI 通过操作系统的原生入口，直接读取状态、调用能力并验证结果。**

ARS 希望建立一套新的系统交互标准：人通过 GUI 使用计算机，AI 通过 ARS Agent Interface 与系统交互。

```text
用户表达目标
     ↓
  AI Agent
     ↓
ARS Agent Interface
     ↓
  操作系统
     ↓
系统服务与应用
```

**AI 应当成为操作系统正式支持的交互主体，GUI 不再是 AI 操作设备必须经过的中间层。**

这里的“直接”指使用系统提供的结构化接口，不是绕过权限、沙箱或应用规则。

> **Status: Concept / Early Research** — 本项目处于概念研究阶段，以下是拟议架构与规范方向，不代表已有可用产品或稳定标准。

## 1. AI 如何直接与系统交互

用户说：

> 将音量调到 30%。

ARS 的目标交互方式是：

```text
AI Agent → 系统音频能力 → Audio Service → 返回实际音量
```

AI 无需打开设置页面、识别滑块并模拟拖动，而是查询系统开放的音频能力，取得所需授权，提交请求并检查结果。

用户说：

> 将购物车里的咖啡改成两件。

AI 通过系统统一入口发现应用开放的购物车能力，读取当前条目，修改数量，再验证业务结果。修改数量的权限不自动包含下单或付款权限。

**系统提供统一入口，系统服务与应用负责各自能力，AI 负责理解目标和组织任务。**

## 2. ARS 要建立什么

ARS 是面向新一代操作系统的原生 Agent 交互标准研究，不是 AI 助手产品、第三方控件、Accessibility 包装或 RPA 框架。

它主要定义三个问题：

- **系统向 AI 开放什么：** 可发现的系统与应用能力，以及结构化状态和执行结果。
- **AI 如何使用这些能力：** 统一的发现、检查、调用、观察、授权和取消规则。
- **谁控制执行过程：** 系统执行权限与安全策略，应用执行业务规则，用户保留确认和接管权。

**规范优先于实现。** ARS 先明确交互契约，再用运行时、平台绑定和参考实现验证。核心标准不绑定某个模型或传输协议。

研究可以在现有操作系统上开展，不要求先构建全新操作系统；原生目标则要求交互入口、身份、授权和生命周期治理纳入系统可信机制。

## 3. 人用 GUI，AI 用 Agent Interface

两种入口应共享同一套业务逻辑与状态：

```text
Human                         AI Agent
  │                               │
  ▼                               ▼
 GUI                     ARS Agent Interface
  │                               │
  └──────────────┬────────────────┘
                 ▼
       共享业务逻辑与状态
                 │
        ┌────────┴────────┐
        ▼                 ▼
     系统能力           应用能力
```

GUI 继续用于展示、编辑、确认和人工操作。Agent 接口用于结构化查询与执行，操作结果也应能通过 GUI 查看。

用户与 AI 同时操作时，运行时需要检测冲突、明确控制权，并在接管后重新同步状态。“共享”描述运行契约，不要求所有组件位于同一进程。

| 组成 | 职责 |
| --- | --- |
| **ARS Agent Interface** | 面向不同 Agent 的统一系统入口。 |
| **ARS Protocol** | 定义能力、状态、操作和授权的交互契约。 |
| **ARS Runtime** | 负责能力调度、状态同步、权限执行、事件与审计。 |
| **Platform Bindings** | 将标准映射到具体平台的接口、权限和生命周期机制。 |

## 4. 系统能力与应用能力

**系统能力**由操作系统或受系统治理的服务提供，例如文件管理、应用启动、音量调整和通知。AI 应通过授权接口使用这些能力，而不是逐页操作设置界面。

**应用能力**由应用开放，例如创建日程、修改购物车和导出文档。系统统一发现与调用方式，应用负责业务含义、数据校验、账号权限与实际执行。

系统无法自动理解任意应用的内部逻辑。应用可以显式开放业务能力，也可以通过框架语义扩展提供有限交互；控件信息能帮助 AI 理解界面，但不能自动证明业务后果。

## 5. 六类统一交互原语

| 原语 | AI 可以做什么 |
| --- | --- |
| `discover` | 发现当前允许获知的系统与应用能力。 |
| `inspect` | 查看能力说明、参数、权限要求和可见状态。 |
| `invoke` | 发起操作，取得结果或可追踪的操作标识。 |
| `observe` | 观察进度、状态变化和最终结果。 |
| `authorize` | 请求或查询授权，由可信策略与必要的用户确认决定。 |
| `cancel` | 请求取消未完成操作，获取实际取消结果。 |

这些原语定义共同语义，不要求固定调用顺序，也不限定具体函数或传输形式。发现能力不等于获得执行权限，AI 不能自行批准权限。

每项能力应说明提供方、版本、输入输出、前置条件、权限、副作用及完成条件，并声明重试和取消规则。

## 6. 操作必须可验证，用户始终有控制权

**执行成功需要业务结果证明。** 请求已接收、控件已响应或页面已变化，都不必然代表任务完成。运行时应关联请求、事件与结果，并处理资源版本冲突、异步执行和断线恢复。

**重试不能重复产生副作用。** 实现需要明确幂等与去重边界；结果未知时先查询或对账。跨应用任务不默认具有事务性。

**权限在执行时检查。** 授权应限制主体、动作、资源与有效期；系统授权不替代应用账号权限，第三方文本不能扩大权限。发送消息、删除数据、付款等操作按策略进入可信确认流程。

**用户可以暂停、取消或接管。** 接管时展示进度与已有副作用，避免双方重复提交；AI 恢复前重新检查状态和授权。取消或撤销授权不等于撤回已经完成的外部操作。

关键操作应可审计，同时限制敏感数据的采集与访问。

## 7. 开发者需要适配什么

ARS 希望让开发者对统一标准适配，减少为不同模型重复开发。应用可以逐步开放能力，不必重写全部界面。

| 参与方 | 适配职责 |
| --- | --- |
| 系统 / 平台 | 提供可信入口、身份权限、事件与生命周期治理。 |
| 应用 | 开放能力，维护描述、业务规则、状态和结果语义。 |
| Agent 客户端 | 遵守契约与授权，处理冲突、失败和人工接管。 |

**现有应用无法无条件兼容 ARS。** 标准控件和语义树可减少基础适配，但不保证完整业务语义；WebView、跨平台框架和自绘界面也各有边界。缺少必要入口的应用需要改造或受限适配器。

Accessibility 与自动化接口可以用于验证部分设计，但不能因此宣称具备完整原生支持。统一协议也不能开放平台禁止的能力或绕过沙箱。

## 8. 规范规划

以下规范尚未正式发布：

| 编号 | 主题 |
| --- | --- |
| **ARS-001** | 核心架构：参与方、能力模型、六类原语、信任边界与符合性。 |
| **ARS-002** | 能力描述与发现：标识、数据结构、检查、版本及兼容性。 |
| **ARS-003** | 执行一致性：调用、状态、事件、结果、错误、幂等、并发与取消。 |
| **ARS-004** | 安全授权：身份、权限范围、委托、确认、撤销及审计。 |
| **ARS-005** | 人机协同：GUI / Agent 状态一致性、控制权转移与恢复。 |

平台绑定拟研究 Android / AOSP、Linux、Windows 等方向，定义具体传输、权限与框架映射，并公开差异和限制。跨平台统一的是契约，不保证功能完全一致。

## 9. 研究路线与当前状态

1. 明确核心架构与典型交互，形成规范草案。
2. 用示例应用和最小运行时验证完整执行过程。
3. 研究现有平台适配与系统级集成，比较实际差异。
4. 建立一致性测试和互操作实验，迭代规范与平台绑定。

目前尚无正式发布的 ARS Protocol、稳定 ARS Runtime 或生产级 ARS Agent Interface，不承诺固定交付日期。参考实现用于验证标准，而非代替标准。

欢迎通过 Issues 或 Pull Requests 讨论架构、应用适配、安全和交互设计；提案请说明具体场景、权限边界及失败路径。

## Vision

> GUI makes systems accessible to people.  
> ARS makes systems readable and actionable for agents.

**操作系统应同时为人类和 AI 提供原生、统一、受控的交互接口。**
